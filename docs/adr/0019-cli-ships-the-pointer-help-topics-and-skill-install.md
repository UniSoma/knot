# The CLI ships the pointer; pull is distinguished by timing, not provenance

[ADR 0017](0017-three-context-surfaces-pull-push-pointer.md) defined *pull* as `knot --help` and `knot <cmd> --help`, "generated from the command registry in `knot.help`, so it cannot drift from the code." That provenance clause is now false for six of the pages `knot help` serves. `knot help lifecycle` prints a hand-written markdown file off the classpath verbatim; nothing about it is generated. **Pull is redefined as what the agent fetches on demand from the installed CLI, versioned with it.** Timing is what separates the three surfaces — pull when the agent asks, push on every turn, pointer when a description fires — and it always was. Drift-proofness is not what makes pull *pull*: it is a property the command pages get from the registry and the topic pages get a different way, by shipping inside the same artifact as the code that answers to them.

The pointer was the one surface 0017 left without a mechanism. A client project got its skill by `cp -r` from a checkout of this repo, so every copy was a snapshot of whatever the repo held that day and drifted against the installed `knot` silently. `doc_flags_test` and `doc_codes_test` exist only to fight that drift *inside* this repo; nothing protected a copy once it left. And a project that installed the CLI and the `SessionStart` hook but no skill could not reach the judgment at all: `prime`'s closing sentence said "invoke the `knot` skill" into a void.

So the CLI carries the skill and hands it out two ways. `knot help <topic>` prints one guide to stdout, for an agent that has a shell and wants the material now. `knot skill install [dir]` writes the whole tree — `SKILL.md`, `references/`, `agents/openai.yaml` — into the directory a harness loads skills from, for an agent that wants it resident. `knot prime`'s closing pointer branches on which of those the project has: it searches `:skill-dir`, then `<project-root>/.claude/skills/knot`, then `~/.claude/skills/knot`, and closes with the invoke-the-skill sentence when it finds a `SKILL.md` or routes the same branch list to `knot help topics` plus an install nudge when it does not. Push never again names a surface that isn't there.

This is not 0017's rejected "generate the skill body from the command registry", and that rejection stands: nothing is generated from the registry, and the pointer's value is still the judgment the registry does not hold. The rejected option is replaced by **the CLI ships the hand-written skill and installs it**. The judgment is authored once, by hand, under `resources/knot/skill/`; the CLI is only the carrier. What that buys is version identity rather than generation: the bytes travel with the binary that interprets them, and the installed `SKILL.md` carries `<!-- installed by knot <version> -->` after its frontmatter, so "the skill and the CLI disagree" becomes a visible version mismatch instead of silent drift.

A **topic** is a noun-named concept guide printed by `knot help <topic>`: `intro`, `lifecycle`, `graph`, `json`, `autonomous`, `writes`. The same files *are* the skill — `intro` is `SKILL.md`'s body, the other five are its `references/` — so one edit under `resources/knot/skill/` moves pull and pointer together, which is the whole point of the arrangement. That does not breach 0017's "one surface each" rule, because the rule counts *authored copies*, not served bytes: what it forbids is two hand-maintained texts of one meaning drifting apart, and a topic is one text that pull prints on demand and the pointer holds resident. Read that way 0017's pointer rule stands, with its letter loosened — the pointer still carries only the judgment no command page holds, and `knot help <topic>` is how that same judgment reaches an agent that has no skill installed. The `help` dispatcher resolves commands, aliases and subcommands before topics, and a test forbids a topic named after any of them, so a future command can never be shadowed by a guide. "Topic" is documentation vocabulary and stays in this ADR beside pull, push and pointer, not in `CONTEXT.md`, which is the ticket glossary. The prior art is uniform on the shape: beads pairs `bd prime` (live state from the binary) with `bd setup <agent>` (matching-version instruction files written out), git ships noun-named guides behind `git help -g` (`gitrevisions`, `gitglossary`), `gh help environment` is a topic beside the commands, and `jj help -k` lists keywords. No shipped first-party CLI was found with a per-command `--ai` flag.

One further clause of 0017 falls. Its consequence "`prime-skill-pointer` is deleted and both sentences inlined" was written because a helper named for preventing drift had failed at it. The closing sentence is built by a helper again, but the shape is different: `output/prime-pointer` composes one of two named branch constants, `prime-pointer-branches-hitl` and `prime-pointer-branches-afk`, with the result of the skill search, and the drift guard is a per-mode test asserting each branch list stays disjoint from the skill description's cold triggers. 0017's real finding holds — if two strings must relate, a test is the mechanism — and a helper standing behind that test is not the thing 0017 deleted.

## Considered options

- **A per-command `--ai` / `--llm` flag** — rejected. It would put the judgment exactly where the agent already is, at the command it is about to run. But the judgment is cross-cutting: the transition gates span `start`, `close`, `status` and `update`; deps versus links spans `dep`, `link` and `show`; autonomous conduct belongs to no command at all. A per-command flag either repeats the same paragraph on six pages or shards one idea across them. Per-command caveats already have their home in `:notes`, which 0017 established for precisely the material that *is* command-scoped.
- **A thin skill whose body shells out to `knot help <topic>`** — rejected. It is the most drift-proof shape available, since the installed copy would hold no judgment to go stale. But it taxes every skill fire with a tool call before a single sentence of judgment is in context, and it fails outright in a harness that reads `SKILL.md` without giving the agent a shell. The version stamp gets most of the same protection for none of that cost.
- **Keep the two copies hand-synced, as 0017 left them** — already rejected there, and this ADR is the bill for the interval in which it was the status quo: a `cp -r` install line in the README, two tests guarding only the in-repo copy, and a push sentence pointing at a file that need not exist.
- **`knot skill install` writes `:skill-dir` into `.knot.edn`** — rejected. It would make the next `knot prime` find the skill with no further step. But install would then edit a committed config on the strength of one invocation, and the usual reason to pass an explicit directory is a machine-specific path like `~/.claude/skills/knot`, which is the last thing that should land in a shared file. An explicit directory that differs from the effective default draws a one-line stderr hint instead, echoing the directory as typed, and the human decides whether it belongs in the config.
- **`knot skill install` clears the target directory before writing** — rejected. It would make a file dropped from a future skill version disappear from every target on the next install. But the target is an arbitrary path the caller names, and a command that takes a path and deletes its contents is the wrong shape to hand an agent. Install overwrites the files it owns and touches nothing else; detecting a lagging install is the version stamp's job (kno-01m21ad0gzs4).

## Consequences

- `resources/knot/skill/` is the single source of the pointer. The copy committed at `.claude/skills/knot/` is an artifact: `knot skill install` regenerates it, and `skill_copy_test` compares the two stamp-stripped, in both directions, so an edit to either side alone fails `bb test`. Editing the pointer means editing `resources/` and re-running the command, which is what AGENTS.md's pointer clause now says.
- `doc_flags_test` and `doc_codes_test` glob `resources/knot/skill/`. They keep the job 0017 gave them — guarding the handful of flags named for their choosing distinction — and now guard the source rather than the copy.
- 0017's no-inventory rule extends to topics. `knot --help` advertises `knot help topics` in one line, and the topic names appear in no prose anywhere, including this ADR's neighbours. The paragraph above names them because defining the term is what an ADR is for; a reader who wants the current list runs the command.
- **`skill_dir` means two different things in two envelopes.** `prime --json`'s `skill_dir` is the *resolved* directory whose `SKILL.md` answered the search, `null` when none did. `info --json`'s `paths.skill_dir` is the *configured* `:skill-dir` echoed back, `null` when unset, with `paths.skill_path` as its absolute form. The `json` topic's path table spells out the difference. Both keys are already shipped, so the fix if this ever bites is a rename with a `schema_version` conversation attached, not a quiet redefinition of either.
- `:skill-dir` is a recognized `.knot.edn` key, read by `skill install` and by `prime`, written by neither. Relative paths resolve from the project root and `~` expands.
- `installed-skill-dir` takes an injectable `:home`, so no test reaches the developer's real home directory. Any future assertion on preamble text through a subprocess has to pin it the same way `prime-ctx` does in `cli_test`.
- 0017 is superseded in three places: its `pull` definition, its rejection of a CLI-produced pointer, and its `prime-skill-pointer` consequence. Its pointer rule is clarified rather than superseded: "nothing that either other surface already states" counts authored copies. Everything else stands unchanged — the irrecoverability ranking, the three per-surface placement rules, and the reason the `afk` preamble keeps its whole loop on push.
