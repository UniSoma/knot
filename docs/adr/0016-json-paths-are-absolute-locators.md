# JSON paths are absolute locators; ids are the portable identifier

The `--json` envelope carries filesystem paths at four sites: `meta.archived_to` on the three transition commands, `data.deleted.path` on `delete`, the six `data.paths.*` keys on `info`, and `data.issues[].path` on the file-level `check` codes. Every one has always shipped absolute, built from a `project-root` that is itself absolute. `references/json-protocol.md` showed them repo-relative in three worked examples, and nothing caught the drift: the contract test asserted `(str/includes? archived-to ".tickets/archive/")`, which is true of both forms. ADR 0015 defined *what* `meta.archived_to` means — a location report, not a movement event — but left *what form that location takes* unstated, which is how a half-promise (documented but unpinned) survived to become a bug report.

We resolve it in favour of the code: knot addresses tickets by **id** and locates files by **path**, and never uses one for the other job. The id is the portable identifier — stable across retitles, closes, machines, and clones, and the only thing any knot command accepts, since no command takes a path argument. A path is a machine-local **locator**, emitted so a consumer can open the file now. Every path in the envelope is therefore absolute and POSIX-separated, and a consumer wanting portability stores the id.

Absolute rather than repo-relative because the project root is discovered by walking up from cwd, so a root-relative path is not openable from a subdirectory — `knot close --json` run from `<root>/sub` reports a root-anchored path, and both terminal hyperlinking and agent file-read tools resolve against cwd, so the relative form breaks silently exactly there. Agent tooling generally requires absolute paths outright; the relative form would force a second `knot info --json` call to join against `project_root`. And relativizing `info.paths` degenerates it: `project_root` becomes `.` and `tickets_path` becomes a restatement of `tickets_dir`. Those fields exist *because* they are absolute. Git looks like a counterexample — `git status --porcelain` is repo-relative — but is not: git paths are addresses in the git command space (`git add <path>`), and knot has no such loop. `check` already obeyed the rule before it was written down, giving file-level issues a path and graph-level issues ids alone.

The form is a contract promise, stated per field in `references/json-protocol.md` and pinned by `fs/absolute?` at all four sites in `json_contract_test.clj`. `info.paths.tickets_dir` is the one exception, asserted *relative*: it echoes the configured directory name (`.tickets`), a config value rather than a locator, and `tickets_path` is its absolute form. The human and JSON surfaces are locked to the same form — both already print absolute, so locking is just recording what ships, and it forecloses a future change to one surface only.

## Considered options

- **Relativize to the project root** — rejected. It is the form the docs claimed, and it would make envelopes diffable across machines and stable in committed fixtures. But it is not openable from a subdirectory without first knowing the root, which is precisely the information the consumer called knot to avoid deriving; it degenerates three of `info`'s six path fields into constants or restatements; and it would make every current consumer's working code wrong for the sake of matching prose that was never true.
- **Emit both: `path` plus a `relative_path` sibling** — rejected. Additive, non-breaking, and cheap. But no consumer has asked for the portable form, two spellings of one fact means half of consumers pick the wrong one, and it is exactly the speculative flexibility the project's guidelines forbid. That adding it later stays non-breaking is itself the argument for not adding it now.
- **Leave the form unspecified and fix only the docs' examples** — rejected. It is the minimal edit and it removes the visible contradiction. But an unpinned form is what produced this ticket: the next refactor is free to relativize one site, no test objects, and the drift recurs with the documentation now vouching for whatever ships.

## Consequences

- `check`'s `data.issues[].path` now flows through `fs/unixify`, which it had been missing since the Windows separator sweep. No POSIX value changes; on Windows `C:\...` becomes `C:/...`. That is a real change on one platform, so it earns a named `fix:` CHANGELOG entry rather than silence.
- `schema_version` stays at `1`. The documented bar is a *shape*-incompatible break (renaming `data`, moving `error.code`); a separator normalization is not a shape change, no POSIX consumer observes it, and documenting an already-emitted field is additive.
- Absolute paths are wrong across a container boundary where the repo is mounted at a different path than the host sees. Knot does not work around this — it is the limitation every path-reporting tool carries — but `json-protocol.md` now states it, so a consumer crossing such a boundary knows to key off ids and rebuild paths itself.
- `data.issues[].path` is documented for the first time, including its conditionality: it appears on `terminal_outside_archive`, `frontmatter_parse_error`, and `missing_required_field` only when the missing field is `:id`. Consumers must treat it as optional and branch on its presence.
- The invariant is not enforced structurally. `fs/unixify` is called at each of the nine emission sites in `knot.cli` rather than once at an envelope-serialization boundary, which is exactly how `check` came to be the straggler: a new path field is correct only if its author remembers the rule. We left it that way deliberately — the alternative touches four unrelated emitters to fix a one-line bug — so the contract tests are what actually hold the line. A future emitter of a fifth path field must add both the `fs/unixify` call and its `fs/absolute?` pin; if a sixth arrives, that is the signal to centralize.
- This ADR succeeds ADR 0015 on the same field: 0015 fixed what `meta.archived_to` asserts, 0016 fixes the form that assertion takes. A future change to either is a contract change to both.
