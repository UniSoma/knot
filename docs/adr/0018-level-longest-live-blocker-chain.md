# Level scores a ticket by its longest live-blocker chain

The three *live* listing commands (`list`, `ready`, `blocked`) gain an **`LVL`** column and a `level` field in `--json`. For a live ticket, level is the length of the longest chain of *live* blockers beneath it through `:deps`, computed over the **live-induced** deps subgraph — `0` exactly when the ticket is `ready`, `n` when some chain of `n` still-open deps must close before it can start. It answers one question: *how many rounds of closes away is this?* Partitioning a set by level yields the order an orchestrator can run it in — level 0 now, level 1 once level 0 closes — so `knot blocked --parent <id> --json | jq 'group_by(.level)'` is the wave order, and no `waves` command is needed.

Level is the **backward** reading of the same graph **Leverage** (ADR 0011) reads forward. Leverage asks what live work a ticket gates; level asks how deep the live work gating *it* runs. The two are orthogonal: a deps-leaf can be level 0 and highest-leverage at once. Level inherits ADR 0011's live-induced traversal wholesale — a closed intermediary is *non-conductive*, so `A → B(closed) → C` leaves A at 0 — for the same reason: only the live "waiting" structure that `ready`/`blocked` already act on is real. It deviates from leverage on exactly one point. **A broken ref is not dropped; it counts as a live leaf blocker.** Leverage may discard a missing referent because a phantom cannot *wait* on anything, but `blocked` already treats an unresolvable dep as gating, so discarding it here would put a blocked ticket at level 0 and break `ready ⇔ level 0` — the equivalence the whole metric rests on.

The crux is what happens when the chain has no end. A ticket on a live `:deps` cycle has no finite longest chain, so its level is `null`, rendered `-`. The decision worth recording is that **`null` is not a cycle-membership test — it is the absence of a finite chain**, and that propagates. A ticket that merely depends *through* a cycle, without sitting on one, is equally without a finite longest chain and is equally `null`. Defining the hole by membership instead would force the alternative: take the maximum over only those children that returned a number. That yields a confident integer computed from a strict subset of the real chains — a *wrong* number, and wrong in the direction that matters, since it under-reports depth for precisely the tickets whose graph is malformed. A cycle is a data error `knot check` reports, not a schedule; the honest answer is to decline to schedule it. `null` is a value, not a failure: no error code, no non-zero exit, and a listing containing a cycle still renders.

Level is **whole-graph, never umbrella-scoped**. A blocker under another parent still gates, so scoping the walk to `--parent` would report a ticket as runnable while something outside the umbrella still held it. `--parent` filters *which rows are shown*; it does not redefine what blocks them.

Per ADR 0011's precedent the surface is minimal: an always-on column and an always-on intrinsic `--json` field, no flag, no sort, no standalone command. Level is absent from the `closed` command, which holds no live rows. On a closed row surfaced the other way — `knot list --status closed` — level is `null`/`-`, because a closed ticket is not a node of the live-induced subgraph at all and is absent from the computed map entirely.

## Considered options

- **`null` only for cycle *members*, maximum-over-numeric-children for everything else** — rejected. Produces a confident integer derived from a subset of the real chains, under-reporting depth exactly where the graph is malformed. A hole in the metric should propagate like a hole, not be silently patched with a partial maximum.
- **Treat a cycle as level `0`** — rejected. Conflates "nothing blocks this" with "we cannot tell what blocks this," and breaks `ready ⇔ level 0`: a ticket on a cycle is `blocked`, not runnable.
- **Error / non-zero exit on encountering a cycle** — rejected. A listing must render on a malformed graph; a data error is `knot check`'s job to report, not a reason to deny the user their backlog.
- **Dropping broken refs, as leverage does** — rejected. Would place a `blocked` ticket at level 0 and break the `ready ⇔ level 0` equivalence. The divergence from leverage is deliberate and is the one place the two metrics read a missing referent differently.
- **Umbrella-scoped level (walk restricted to `--parent`)** — rejected. Would report a ticket as level 0 while a blocker outside the umbrella still gated it. Filters choose rows, not semantics.
- **A `knot waves` command, or a `--level N` filter** — rejected, per ADR 0011's precedent. `group_by(.level)` over the existing `--json` composes with every other filter for free; a command would re-implement that composition.
- **Per-row recomputation, mirroring `leverage`'s shape** — rejected for one memoised depth-first pass over the corpus returning `{id → level}`, following `connected-components`/`annotate-cc` instead. The memo is written only after a subtree is fully explored — the on-stack branch returns without memoising — so a cached value never depends on the path that reached it.

## Consequences

- `query/levels` lands beside `leverage` and `coupling`: one memoised DFS over the live-induced deps subgraph, cycle-guarded by an on-stack path set, keyed only by live tickets.
- `list`, `ready` and `blocked` render `LVL` and emit `level`. `closed`, `show`, `dep tree`, `check` are untouched.
- Consumers must handle `level: null`. It is the documented signal for "this ticket's deps graph contains a cycle, here or beneath it" — the one case where reading the column should send you to `knot check` rather than to work.
- **`LVL` diverges from `LEV`/`CPL` on closed rows.** Under `knot list --status closed`, leverage and coupling still print computed numbers while level prints `-`. Level's `-` is the position this ADR takes: those metrics are defined over the live-induced subgraph, and a closed ticket is not in it. That `LEV`/`CPL` answer anyway is a pre-existing wart this ADR does not fix — ADR 0011 declared leverage absent from `closed` and the `--status closed` path was not covered.
- `CONTEXT.md`'s **Level** entry is the glossary home for the term; its `_Avoid_` list steers off "depth" (ambiguous with the parent tree), "wave" (a consumer's name for a set sharing a level, not a ticket property) and "tier"/"rank" (imply priority).
