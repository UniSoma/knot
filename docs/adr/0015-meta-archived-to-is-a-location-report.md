# `meta.archived_to` is a location report, not a movement event

A ticket's status determines which directory holds its file: terminal statuses live under `.tickets/archive/`, everything else under `.tickets/`. `knot.store/save!` performs that routing on every write, so any command that changes a ticket's status can move its file — and three commands can: `close`, `status <id> <new>`, and `update <id> --status <new>`. The `--json` envelope's optional `meta` slot exists so a consumer tracking ticket files doesn't have to re-derive the path itself.

`update --status <terminal>` shipped through v0.9.0 performing the archive routing while emitting no `meta` at all, because the reporting was duplicated per-command in `knot.cli` rather than shared. A JSON consumer that treated an absent `meta` as "the file didn't move" silently lost the file on exactly that call. Fixing it forced the question the slot had never actually answered: what does `meta.archived_to` *assert*?

We define it as a **location report**: *"this ticket is in the archive, at this path."* It is emitted whenever the resulting `data.status` is in `:terminal-statuses`, by all three transition commands, whether or not the call moved a file. An absent `meta` therefore means the ticket is in the live directory. There is no `restored_to` counterpart — the un-archiving direction (`reopen`, `status <id> <non-terminal>`, `update <id> --status <non-terminal>`) reports nothing, because a non-terminal `data.status` already carries that fact and the path is the project's one live directory.

The key is derived from the resulting status, not from which flags the caller passed, so two calls that leave a ticket in the same state emit the same envelope. A single private `archive-meta` helper in `knot.cli` computes it for every transition path, so the reporting cannot drift from the routing again — the drift this ADR responds to was in the reporting, not the routing, which had been shared all along.

## Considered options

- **Movement event: emit iff the file actually changed directory** — rejected. Semantically the tightest reading, and it would make the slot a true event channel. But it withdraws the emission on a re-close of an already-closed ticket, which is shipped behaviour pinned since the v0.3 contract test suite; it requires `save!` to report whether it crossed a boundary, changing a return shape 13 call sites consume for one consumer's benefit; and it makes the envelope depend on prior on-disk state, so a consumer can no longer predict the shape from the request plus the response's own `data.status`.
- **Full-duplex location channel: add `restored_to` for un-archiving** — rejected. Superficially the symmetric answer, and it would let a consumer track location purely off `meta`. But the live path is a single project-wide directory that `knot info` already exposes, so the key would carry no information `data.status` doesn't. It widens the wire contract and adds a second key to keep in sync for a case with one possible value.
- **Refuse a terminal `--status` on `update`, pointing at `close`** — rejected. Narrows the surface instead of fixing the report, and it deletes the one-call check-and-close idiom (`knot update <id> --ac "last AC" --done --status closed`) that both `SKILL.md` and `references/lifecycle-gates.md` recommend, replacing it with a two-call sequence that has a window where the AC is checked but the ticket is still open. `update` is not a lesser command that grew a status flag by accident: it already enforces the acceptance gate, the open-children gate, `--summary`, and `--force`. It is a peer transition path and owes the peer contract.
- **Emit `meta` only when `--status` was explicitly passed to `update`** — rejected. Keeps a field-only update on an archived ticket silent, which reads as narrower and safer. But it keys the envelope on invisible input rather than on observable state: two calls leaving the ticket in identical condition would differ, and a consumer would have to remember its own request to interpret the response.

## Consequences

- `update <id> --json` on a ticket whose resulting status is terminal now emits `meta.archived_to` even with no `--status` flag — e.g. `update <archived-id> --priority 1 --json`. This is intended and pinned; the path is the ticket's current location, which is what a file-tracking consumer needs.
- The addition is purely additive to the envelope, so `schema_version` stays at `1` per the documented rule (it bumps only on shape-incompatible breaks).
- `reopen`'s silence is now specified rather than incidental. A future reader who notices it moves a file and reports nothing will find this ADR instead of re-filing the bug pointing the other way; the un-archive case is pinned negatively in `json_contract_test.clj` so restoring symmetry has to be a deliberate contract change.
- The `meta` slot remains single-key and transition-only. Non-transition mutations (`dep`, `undep`, `link`, `unlink`, `add-note`, `create`, `migrate-ac`) omit it regardless of the ticket's status — they are not transition paths and do not report location.
- Left open here and since settled in ADR 0016: `meta.archived_to` shipped an absolute path while `references/json-protocol.md` documented it repo-relative, and the contract test's `str/includes?` assertion passed for both forms. 0016 resolves it in favour of the code across all four path sites — this ADR fixed *what* the field asserts, 0016 fixes *what form* that assertion takes.
