# Cascade removes destroyed dependents last

ADR 0008 fixed one write order for `knot delete --cascade`: referrers first, target last, abort before unlinking on a partial-cleanup failure. That order was derived from a single case — every dependent was a ticket that gets *rewritten* — and stating it as a fixed sequence rather than as the rule behind it left no guidance for a dependent of a different kind. Documents are that kind: a cascade **destroys** them rather than rewriting them.

The rule is: **remove last whatever leaves a reportable intermediate state.** A dependent side that is *rewritten* goes first, because until it is rewritten it holds a reference that will dangle the moment the target disappears, and a dangling reference is a fault the tracker would report against a ticket that no longer exists. A dependent side that is *destroyed* goes last, because until the target disappears the dependent is legitimately attached, and destroying it first produces a state nothing can report.

The asymmetry is forced rather than chosen, and ADR 0016's id-versus-path split is why. A document names its owning ticket in its own frontmatter and the ticket stores nothing about its documents — the relation is read backwards, by scanning the document corpus. So a ticket that lost its documents mid-cascade is **byte-identical** to a ticket that never had any. There is no field to be missing, no count to disagree with, nothing for `knot check` to notice. Documents-first would make an interrupted cascade both unrecoverable and undetectable. Documents-last leaves orphaned documents naming a ticket that resolves to nothing, which `check` already reports under `doc_unknown_ticket`, path included. The operator can restore the ticket from git or delete the orphans; either way they are told.

Reportability is the whole justification, so it is load-bearing and tested rather than asserted: the fault-injection test in `cli_test` interrupts the cascade at the document-removal step and asserts that the ticket is already gone, that the documents survive, and that a subsequent `check` run reports them.

## Considered options

- **Documents first, then referrers, then the target** — rejected. It is the intuitive reading of "clean up the dependents, then the thing" and it means the target is never the last write, so an interrupted run always leaves the target present and re-runnable. But the surviving target is indistinguishable from one that never owned documents, which converts a recoverable interruption into silent data loss. The fact that the operation is re-runnable is worth nothing when nobody can tell it needs re-running.
- **Delete the documents and the ticket in one atomic step** — rejected. It would remove the ordering question entirely. But knot has no transaction boundary and deliberately none: ADR 0008's whole design is a sequence of independent file writes with a stderr breadcrumb, and the tracker has no daemon, no index and no lock to build one on. Adding a journal for the one command that destroys dependents is a new failure mode, not a removed one.
- **Refuse `--cascade` on a ticket owning documents; require removing them by hand first** — rejected. It is the safest possible answer and needs no ordering rule at all. But it makes the common case — delete a ticket and everything attached to it — a manual loop over ids the operator has to list first, and `--cascade` exists precisely to be that loop. The bare `delete` already refuses and enumerates both the referrers and the documents; that is where the deliberate stop belongs.

## Consequences

- This ADR succeeds ADR 0008 on the same command: 0008 fixed which writes a cascade performs, 0022 fixes what orders them. A future change to either is a contract change to both. 0008's success contract is untouched — it is scoped to a *successful* delete, and a successful cascade still ends with every referrer rewritten, the target unlinked and nothing dangling.
- The storage rule and the ordering rule are reciprocal. Storing a document list on the ticket (contradicting the backwards-read rule) would make documents-first detectable and reopen this decision; changing the removal order would make that storage decision matter. Whichever moves first must say so here.
- The bare-`delete` refusal now fires on owned documents as well as incoming references, and the `has_incoming_refs` payload gains a `documents` array. The code name stays: the documents *are* incoming references, read backwards.
